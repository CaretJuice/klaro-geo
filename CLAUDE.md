# Klaro Geo

## Project Overview

Klaro Geo is a WordPress plugin that provides geo-targeted consent management using the Klaro consent library. It applies a different consent template (opt-in, opt-out, and so on) depending on the visitor's country or region, drives Google Consent Mode, and can record consent receipts.

## Architecture

Three rules shape the frontend. Follow them in every change.

1. **Klaro's manager is the source of truth for consent state.** Read consent from `window.klaro.getManager()` (through `KlaroGeoEvents.getConsentState()`), never from a copy.
2. **The dataLayer is output only.** Every significant event is pushed to `window.dataLayer` so tag managers and analytics can react. Plugin code must not read its own settings or consent state back out of the dataLayer.
3. **`window.klaroConsentData` is the one settings object.** PHP builds it in `klaro_geo_build_consent_data()` and emits it once per page. Frontend scripts read settings from it. Do not add a second copy with `wp_localize_script`.

Events use this wrapper, with `eventSource` of `klaro` (forwarded from Klaro) or `klaro-geo` (generated by the plugin):

```javascript
{
  'event': 'Klaro Event',
  'eventSource': 'klaro-geo',
  'klaroEventName': '<specific_event_name>',
  // Event-specific data...
}
```

`Klaro Consent Update` is the exception: it has its own event name because it is the event tags fire on and the event that releases the consent queue.

## Specs: contracts only

`specs/` holds contracts between sides that are written separately and cannot be changed together. It is not documentation of how each file works.

| Spec | Contract between |
|------|------------------|
| `specs/datalayer-events.spec.yaml` | The plugin and readers of the dataLayer outside this repo (GTM containers, the traffic-diagnostics adapter) |
| `specs/consent-queue.spec.yaml` | The plugin and callers of `window.klaroGeo.push()` (themes, other plugins, GTM custom HTML) |
| `specs/frontend-data.spec.yaml` | PHP and JavaScript (`klaroConsentData`, the fields added to `klaroConfig`), plus the consent keys GTM tags reference |
| `specs/client-side-geo.spec.yaml` | PHP and JavaScript template resolution, which is implemented in both and must agree |

Rules:

- If a change alters anything a spec describes, update the spec in the same commit. For `datalayer-events` and `consent-queue` that is a breaking change for people outside this repo: add an entry under `breaking_changes` and mention it in the changelog.
- Do not write a spec for a PHP class or a single file. Internal behaviour is protected by tests, with the reasoning in a code comment next to the code.
- A spec that disagrees with the code is a bug. Fix whichever is wrong; do not leave them out of step.

## Business rules live in tests

When a rule matters, there is a test that fails if it is broken. Before changing behaviour in one of these areas, read the tests listed, and when you fix a bug add a test that would have caught it.

| Rule | Tests |
|------|-------|
| Templates: database values are preferred over hardcoded defaults; defaults are used only when the database is empty or corrupt | `ContractVerificationTest.php`, `klaroGeoCorruptTemplateConfigTest.php` |
| Template resolution: region, then country, then the fallback template; the key returned always exists | `ContractVerificationTest.php`, `tests/fixtures/geo-resolution-parity.json` (run against PHP and JS) |
| `cookieDomain`: empty means auto-detect from the site URL with a leading dot; non-empty is used exactly | `ContractVerificationTest.php` |
| Never give Klaro a global `required: true` (its Decline button then accepts everything); Required is resolved per service | `klaroGeoTemplateRequiredTest.php` |
| Consent defaults and consent keys | `klaroGeoConsentModeTest.php`, `tests/js/test-consent-mode.js` |
| Which services GPC switches off by default | `klaroGeoGpcSensitivityTest.php`, `tests/js/test-gpc.js` |
| Consent receipts: validation, when logging is enabled, storage | `klaroGeoConsentReceiptStorageTest.php` |
| Consent queue | `tests/js/test-consent-queue.js` |

Tests must call the plugin's real functions. Do not add a helper that re-implements production logic so a test can call it, and do not assert on data the test built itself. If production code is hard to test (for example an AJAX handler that exits), restructure it so the logic sits in a function that returns a value, and test that.

When fallbacks are used (template not found, hardcoded defaults, `cookieDomain` auto-detection failing), log it with `klaro_geo_debug_log()`. Never fall back silently.

## Checks: at the boundary, not everywhere

Data is untrusted in the places below. It is validated there, once, and trusted after that. Do not re-check it further in.

| Boundary | Checked by | After that |
|----------|------------|------------|
| `$_GET` / `$_POST` / AJAX request bodies | the sanitize functions (`klaro_geo_sanitize_receipt()`, `klaro_geo_sanitize_services()`, and so on) | Typed and trusted |
| Options read from the database | the `Klaro_Geo_Option` classes, which fall back and log when a value is corrupt | Always an array of the documented shape |
| `window.klaroConsentData` and the template payload, in JavaScript | PHP builds them; `specs/frontend-data.spec.yaml` is the contract | Read fields directly |
| Things the plugin does not control: geoip-detect, `window.klaro` before it loads, `navigator.globalPrivacyControl`, `localStorage`, `fetch` | the one function that touches each | Callers do not re-check |

Rules:

- A guard must be able to fail. Before writing `isset()`, `is_array()`, `typeof x !== 'undefined'` or a `try`, name the real input that makes it false or throw. If there is none, leave it out.
- `try` / `catch` only around what throws (JSON parsing, `localStorage`, `fetch`), and the `catch` must do something: fall back and log, or report.
- Production code never behaves differently under test. No `WP_TESTS_DOMAIN`, `process.env` or similar outside `tests/`. If a test needs different conditions, the test sets them up (see `tests/phpunit/bootstrap.php`).
- Do not guard the plugin's own functions with `function_exists()`; its files are always loaded.
- `wp_send_json_*()` ends the request. Do not follow it with `exit`.
- Log through `klaro_geo_debug_log()` in PHP and `klaroGeoLog()` / `klaroGeoWarn()` / `klaroGeoError()` in JavaScript, never `console.*` directly, and do not type a prefix into the message (the helpers add one). Log decisions, fallbacks and skips. Do not log that a function was entered, a file loaded or a step completed.
- Before writing a helper, search for one that already does the job.

`bin/check-banned-patterns.sh` fails on the patterns above that can be matched mechanically. It runs in pre-commit (`pre-commit install` once after cloning) and can be run by hand.

## Security rules

- Every admin AJAX handler and form handler checks a nonce and `current_user_can( 'manage_options' )`. A nonce alone is not authorization.
- Do not print admin nonces on the frontend.
- Sanitize input where it enters: `sanitize_text_field()`, `absint()`, `wp_unslash()` on `$_GET` / `$_POST`. Escape output where it is echoed: `esc_html()`, `esc_attr()`, `esc_url()`.
- The consent receipt endpoint is public and never refuses a request for its nonce (a nonce in a cached page expires, and a lost receipt is a lost consent record). Treat everything it receives as hostile: it goes through `klaro_geo_sanitize_receipt()`, which stores consent choices as booleans only. A receipt is recorded against a user ID only when the request carries that user's valid nonce (`klaro_geo_receipt_user_id()`).
- In admin JavaScript, insert data with `.text()` or DOM APIs, never by concatenating it into `.html()`.
- Use `$wpdb->prepare()` for queries with variables.
- Do not return database or exception messages to unauthenticated callers; log them.

## Local Environments (Docker)

All WordPress environments for this plugin live in this repo; there are no shared containers elsewhere on the machine. Use Docker Compose v2 (`docker compose`, not `docker-compose`). In every stack the repo is bind-mounted at `/var/www/html/wp-content/plugins/klaro-geo`, so code edits are live without a restart.

| Stack | Compose file | Run from | URL / container | Use for |
|-------|--------------|----------|-----------------|---------|
| PHPUnit runner | `docker/docker-compose.yml`, service `wordpress_test` (+ `db_test`) | `docker/` | one-off container | PHP test suite |
| E2E site | `docker-compose.e2e.yml` | repo root | http://localhost:8080, container `klaro-geo-wordpress-e2e` | Playwright tests, reproducing frontend bugs in a real browser |
| Dev site | `docker/docker-compose.yml`, service `wordpress` (+ `db`) | `docker/` | http://localhost:8000 | Manual testing; avoid (see warning) |

**Tests:**
- PHP: `cd docker && docker compose run --rm wordpress_test vendor/bin/phpunit` (add `--filter ClassName` for one test class). The bootstrap turns the plugin's debug logging on; its output lands in `docker/logs/debug_test.log`, not in the terminal.
- JS: `npx jest` from the repo root, on the host (no container needed).
- E2E: `npm run e2e:setup` (starts the E2E stack and waits), `npm run e2e:test`, then `npm run e2e:docker:down`. The suite runs with one worker because the tests share one site and change its options; do not turn parallelism back on. A full run takes about two and a half minutes.

**E2E site** (preferred for anything that needs a running WordPress):
- Start with `docker compose -f docker-compose.e2e.yml up -d`; ready when `docker logs klaro-geo-wordpress-e2e` prints `E2E Environment Ready!`.
- The entrypoint installs WordPress unattended, activates klaro-geo and geoip-detect, and sets GTM ID `GTM-M2Z9TF4J`. Admin login: `admin` / `password`.
- WP-CLI: `docker exec klaro-geo-wordpress-e2e wp --allow-root --path=/var/www/html <command>`, e.g. `option get klaro_geo_services` or `eval 'echo json_encode(get_option("klaro_geo_templates"));'`.
- Playwright and its browsers are already installed (`node_modules/playwright`, `~/.cache/ms-playwright`). Ad-hoc scripts can `require()` the absolute path to `node_modules/playwright`.
- Plugin JS debug logging is off by default; in a Playwright context, `addInitScript(() => { window.klaroGeo = { debugEnabled: true }; })` turns it on.

**Warning, dev site:** `docker/docker-entrypoint-wordpress.sh` runs `chown -R www-data` and `chmod -R a+w` on the bind-mounted plugin directory, which changes ownership and permissions of the host checkout. Use the E2E site instead unless the user asks for the dev site. (The test runner's entrypoint was fixed for this in 591ebfc.)

## Production Debugging: caretjuice.com + traffic-diagnostics

caretjuice.com is the only live install of this plugin. It also runs the traffic-diagnostics instrumentation from `/home/damon/dev/ca/research/traffic-diagnostics/`, which records consent behavior **outside** Klaro, so it can confirm what the plugin actually did for real visitors. Use it as a debugging source for consent problems, after reproducing locally on the E2E site.

- **What it records per page load:** the `cmp` phase (which Klaro Geo template was applied and the geo detected) and the `consent` phase (what the visitor granted, and whether they acted on this page or a stored choice or the defaults applied: `cmp_event` = `set` / `load` / `default`). caretjuice.com also records the `gtag('consent', ...)` commands the plugin sends, including the custom `*_consent` keys.
- **Where the data is:** BigQuery. The project, dataset and site config are in that repo's `deployment.yaml` (gitignored, the source of truth). Field meanings are in its `docs/FIELDS.md`, and the Klaro Geo adapter is `client/presets/klaro-geo.js`. Read that repo's `CLAUDE.md` before changing anything there.
- **Low traffic:** caretjuice.com gets single-digit visits per day. After deploying a fix, wait several days before drawing conclusions, and compare windows before and after the deploy date. A day or two of data is anecdote, not evidence.
- If a plugin change alters the dataLayer events, consent keys or template data the adapter reads, check `client/presets/klaro-geo.js` in that repo still parses them.

## Before Any Code Change

1. Read the tests for the area you are changing (see "Business rules live in tests").
2. If the change touches the dataLayer, the consent keys, `klaroConsentData`, `window.klaroGeo.push()` or template resolution, read the matching spec and update it in the same commit.
3. If it changes dataLayer events or consent keys, check `client/presets/klaro-geo.js` in the traffic-diagnostics repo still parses them.
4. Run the PHP and JS suites before committing. Run the E2E suite for anything that changes frontend behaviour.

## Commit Workflow

**IMPORTANT**: Commit after each meaningful change that passes tests.

### When to Suggest a Commit

Suggest using `/commit` after:
- A bug fix is complete and tests pass
- A new feature is implemented and tested
- New tests are added
- A contract spec is updated
- Documentation is added or updated
- Refactoring is complete and tests pass

### How to Commit

Use the custom `/commit` command which:
1. Runs the full test suite
2. Only commits if ALL tests pass
3. Generates an appropriate commit message

### Commit Guidelines

- **Atomic commits**: Each commit should be one logical change
- **Minor fixes can be rolled up**: Small related fixes can be combined
- **Always test first**: Never commit without running tests
- **Clear messages**: Commit messages should explain the "why"

### Commit Types

- `fix:` - Bug fixes
- `feat:` - New features
- `test:` - Test additions/changes
- `docs:` - Documentation changes
- `refactor:` - Code refactoring
- `chore:` - Maintenance tasks
